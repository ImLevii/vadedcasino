# Admin payment providers

Open **Admin → Cashier → Payment providers** (`/admin/cashier?type=providers`). The Providers tab manages PayPal, Stripe, Apple Pay, Cash App Pay, SkinDeck and gift cards. Transactions and Provider audit show payment requests, manual approvals and administrative changes. Historical crypto records are available under **Archived crypto**.

## Supported flows

- PayPal: email deposits with manual staff approval (the default for new configurations), or optional Orders v2 checkout and server-side capture. Payouts v1 withdrawals still require API credentials and merchant access. Previously saved configurations keep API checkout until an admin changes the deposit flow.
- Stripe: Checkout Sessions and Connect transfers to accounts created and bound to the authenticated user. A transfer completes when delivered to the connected Stripe account; bank payouts follow Stripe’s own schedule. This is not a transfer to an arbitrary bank account.
- Apple Pay: a separate deposit method (`/deposit?type=applepay`) using Stripe hosted card checkout. Apple Pay is offered when the device, browser and Wallet are eligible; card checkout remains available as a clearly labelled fallback. This integration does not implement Apple Pay disbursements.
- Cash App Pay: a separate deposit method (`/deposit?type=cashapp`) using Stripe hosted checkout with `payment_method_types=['cashapp']`, USD amounts and Cash App approval/QR authentication. This integration does not send payouts to a `$cashtag`.
- SkinDeck and gift cards keep their existing flows and admin controls. Their fees and limits remain governed by their existing implementation.

Apple Pay and Cash App Pay have independent switches, limits, fees, encrypted credentials, webhook endpoints, histories and admin transaction filters. Their withdrawal settings are unsupported and disabled; withdrawal API requests are rejected before reserving any funds. They use Stripe as the processor, not separate Apple or Cash App server credentials. Stripe API keys may be shared across methods, but each webhook endpoint needs its own signing secret saved in its provider configuration. Existing Stripe credentials stored in admin are not automatically copied into the wallet configurations. Environment `STRIPE_TEST_*` values can supply defaults.

Sandbox and live mode are configurable in admin for PayPal, Stripe, Apple Pay and Cash App Pay. The application does not enforce a casino-specific prohibition or require a PayPal approval-reference entry. This setting does not change processor-side merchant eligibility, account capabilities or approval. PayPal Payouts access and Stripe Connect capabilities still come from the processor.

Sandbox payment creation is restricted to OWNER/ADMIN staff. Sandbox completion never changes player balances, held funds, deposit rewards or the financial ledger. Test records are marked separately throughout admin and customer payment history. New hosted-checkout methods default to disabled sandbox mode.

## Credentials and setup

1. Provider credentials can be entered and updated entirely in admin; no provider environment variables or separate `PAYMENT_SETTINGS_KEY` are required. By default, the vault derives its encryption key from the existing server `JWT_SECRET` using HKDF-SHA256 with a separate payment-vault context. The existing application secret must be stable and at least 32 bytes. Back it up with the database: changing it makes application-key credentials unreadable. An independent 32-byte `PAYMENT_SETTINGS_KEY` (64 hex characters or base64) remains optional; keep the original key for previously encrypted records. Records identify their key source so adding an independent key does not break application-key records. Saving a provider re-encrypts its credentials using the currently preferred key.
2. Enter **Public API origin** and **Public frontend origin** in each hosted-checkout provider configuration (HTTPS in production, without paths or query strings). These override `BASE_URL` and `FRONTEND_URL`, which remain optional fallbacks. Hosted checkout returns to `/deposit`; Connect onboarding returns to `/withdraw`. A saved API origin is also the default frontend origin when that field is blank.
3. Configure credentials in admin. Values are encrypted with AES-256-GCM and provider-bound authenticated data. Reads return only presence/source indicators. Empty fields retain saved values. Removing a stored value restores any environment fallback.
4. For PayPal email deposits, select **Email + manual approval**, enter **Receiving PayPal email**, and enable deposits in the desired environment. No client ID, client secret, webhook ID, merchant ID or public return URL is required for this deposit flow. API checkout and withdrawals still need the API credentials. PayPal sandbox/live credentials are independent. Environment fallbacks are `PAYPAL_TEST_CLIENT_ID`, `PAYPAL_TEST_CLIENT_SECRET`, `PAYPAL_TEST_WEBHOOK_ID`, `PAYPAL_TEST_MERCHANT_ID`, and the corresponding `PAYPAL_LIVE_*` names. Generic `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_WEBHOOK_ID`, and `PAYPAL_MERCHANT_ID` apply only to `PAYPAL_MODE` (sandbox by default).
5. Stripe, Apple Pay and Cash App Pay accept secret `sk_test_` / `sk_live_` keys and restricted `rk_test_` / `rk_live_` keys for the matching mode (with the necessary account/Checkout permissions). Publishable `pk_` keys cannot be used for server requests. Credentials are stored separately for each mode. Optional environment fallbacks are `STRIPE_TEST_SECRET_KEY` / `STRIPE_TEST_WEBHOOK_SECRET` and `STRIPE_LIVE_SECRET_KEY` / `STRIPE_LIVE_WEBHOOK_SECRET`. Generic Stripe keys are accepted only when their prefix matches the selected mode.
6. **Check configuration** for PayPal email deposits validates the local configuration; it does not contact PayPal or verify email ownership or receipt. API PayPal **Check connection** verifies OAuth access and the configured webhook’s existence. Stripe, Apple Pay and Cash App Pay **Check connection** read the platform account. This is a connectivity check, not merchant approval or a guarantee of payout eligibility/funding. SkinDeck/gift-card **Check configuration** verifies local configuration without creating a provider payment.
7. Save limits and fees in USD for hosted-checkout methods. The server snapshots the existing coin conversion rate, fiat amount and fees into every payment. Deposit fees are added to the amount charged; supported withdrawal fees are deducted from the recipient’s amount. Every withdrawal requires admin review before any external transfer.

Admin changes require an authenticated OWNER/ADMIN session, version matching, an idempotent request ID and a reason. Secrets never appear in responses or audit results. API credentials cannot be changed while unfinished payments in their mode still require them. PayPal receiving emails can be changed with open payments: email deposits keep their saved recipient, and automatic checkouts and payouts do not use that setting. Manual email deposits do not prevent API credential changes. Hidden credential fields are omitted when saving a different deposit flow.

## PayPal email deposit review

Players create a deposit at `/deposit?type=paypal`. The server records the receiving email, coins, exact USD amount including fees, mode and payment reference. The player sends the payment in PayPal, includes the reference in its payment note, and keeps the receipt. Refreshing the page or opening PayPal does not approve a payment. Email deposits remain `awaiting_payment` until staff reviews them. Staff sandbox requests use a sandbox PayPal link and never add coins.

In **Cashier → Payment providers → Transactions**, use **Approve deposit** after confirming the PayPal receipt, receiving email, exact amount and reference. Enter the actual PayPal transaction ID, confirm receipt and give a reason. The receipt ID, balance credit, deposit rewards, ledger and audit record commit together. Replaying the same approval does not credit twice; another request cannot reuse that receipt in the same environment. API capture and reconciliation endpoints cannot approve an email deposit.

**Reject deposit** closes an unapproved request without changing any balance. If a player already sent funds, investigate the receipt before rejection; this action does not send a PayPal refund. Previously saved API checkouts and payouts retain their original flow and can still be reconciled after changing the deposit setting. Updating the receiving email affects new deposits only; retries and existing requests keep the original email and amount. Outstanding API payments still prevent changing the API keys they need for settlement.

## Retired providers

CoinPayments, MEXC and Zebra are removed from the provider dashboard and customer payment methods. Their creation routes and configuration/activation controls return HTTP 410 `PAYMENT_PROVIDER_REMOVED`, regardless of previously saved switches or credentials. Deprecated crypto/card feature switches cannot reactivate them. Cryptocurrency deposits/withdrawals and Zebra card checkout are no longer offered; Stripe card checkout remains available through the configured sandbox or live mode.

Financial history, previously issued deposit-address callbacks, signed Zebra callbacks, cancellation/refund of queued crypto withdrawals and read-only reconciliation of previously submitted MEXC transfers remain operational. Archived crypto cannot approve or send a new payout. Existing records and stored credentials are retained for settlement and audit. Keep the previous master key and callback/exchange credentials available until all historical payments are resolved; these removed providers are omitted from the new `.env.example` setup list. No historical table or balance is deleted.

## Provider webhook subscriptions

Use the API domain for these endpoints:

| Provider          | Endpoint                                         | Subscribe to                                                                                                                                                                    |
| ----------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PayPal test       | `/trading/providers/paypal/webhook?mode=sandbox` | `CHECKOUT.ORDER.APPROVED`, `PAYMENT.CAPTURE.COMPLETED`, `PAYMENT.CAPTURE.REFUNDED`, `PAYMENT.CAPTURE.REVERSED`, `CUSTOMER.DISPUTE.CREATED`, and `PAYMENT.PAYOUTS-ITEM.*` events |
| PayPal live       | `/trading/providers/paypal/webhook?mode=live`    | The same events, registered in the live application                                                                                                                             |
| Stripe            | `/trading/providers/stripe/webhook`              | `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.expired`, `transfer.created`, `charge.refunded`, `charge.dispute.created`           |
| Apple Pay         | `/trading/providers/applepay/webhook`            | `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.expired`, `charge.refunded`, `charge.dispute.created`                               |
| Cash App Pay      | `/trading/providers/cashapp/webhook`             | The same checkout/refund/dispute events as Apple Pay                                                                                                                            |

Keep callbacks enabled when stopping new deposits or withdrawals. Stripe sandbox and live endpoints share the same path and select mode from the signed event; configure the appropriate signing secret for each mode. Stripe signatures use the original JSON bytes with a five-minute timestamp tolerance. PayPal events are checked through its verify-webhook-signature API. The server then retrieves the original checkout or payout and verifies its identity, recipient, USD amount and completion state. A redirect or unverified webhook cannot credit coins.

Duplicate and concurrent confirmations settle at most once. Settlement, balance changes, held funds, rewards and ledger entries commit atomically. Refund/dispute callbacks flag the payment for financial review and lock the affected live account; they do not automatically initiate another external refund or create a negative balance. Verified refund/dispute references are retained even before confirmation arrives, preventing delayed confirmation from crediting a payment already under review.

## Deposit completion and balance updates

Stripe, Apple Pay, Cash App Pay and automatic PayPal deposits use the same settlement transaction for webhooks and authenticated recovery. Returning from checkout, returning focus to an open payment, and **Refresh payment status** verify the saved payment with the provider before crediting. Visible pending payments retry verification every 15 seconds; manual email deposits and withdrawals only refresh their saved status. A successful redirect alone never credits coins. PayPal recovery verifies the original merchant, amount and reference before capturing an approved order. Completed confirmations do not submit another capture or add another credit.

PayPal email deposits credit after staff approves a verified receipt. Gift-card redemption credits within its redemption transaction. SkinDeck verified success can credit a deposit that was previously marked failed, cancelled or expired, while already completed trades stay protected against duplicate credit.

Payment completion, gift-card redemption and completed SkinDeck trade history refresh the authoritative account balance over HTTP, including when the socket is disconnected. Socket updates use the same balance reader, so simultaneous callbacks and browser refreshes cannot apply a deposit amount twice. The UI never computes a new balance from the payment amount. Webhooks remain required for customers who do not return to the site; follow [Stripe's fulfillment guidance](https://docs.stripe.com/checkout/fulfillment) when configuring provider endpoints.

## Payout review and recovery

Player withdrawal requests reserve live coins and enter `queued`. **Approve** commits a `sending` claim before contacting the provider. Duplicate approvals never send twice. **Deny** applies only to queued withdrawals and refunds their held coins once. After submission, use **Reconcile** instead of denying or creating a new transfer.

Timeouts and lost responses remain `unknown` with the balance reserved. A confirmed success releases held funds without another debit. A provider-confirmed failure releases and refunds held funds once. An absent transfer is not proof of failure. PayPal requests with a lost batch ID need the original provider callback or provider support to confirm the batch; reconciliation never issues a new payout to discover the old one. Stripe reconciliation can retrieve a known transfer or search up to 500 recent transfers to the saved connected account, keeping funds reserved if no match is confirmed.

Checkout retries reuse their original provider key. Requests older than five hours for PayPal or 23 hours for Stripe must be investigated rather than recreated with an expired provider idempotency key. Payout submission has a durable local claim and is never automatically repeated.

## Schema and verification

`database/migrations/009_payment_providers.sql` adds `paymentProviders`, `providerPayments`, `providerAccounts` and `providerDisputes`. `runtime/cashier.js` also creates these tables at startup for existing installations. MySQL and PostgreSQL installation schemas include the same tables. No credentials are seeded and no payment method is automatically activated.

Run `node --test tests/payment-vault.test.js tests/payment-providers.test.js tests/paypal-email.test.js tests/cashier-schema.test.js tests/cashier.test.js tests/skindeck/core.test.js`. The provider suite runs the real Express routes against isolated embedded PostgreSQL with mocked HTTP providers: role/session checks, credential encryption/redaction without a separate master key or provider environment credentials, admin URL overrides, sandbox/live credential separation, live Stripe/wallet settlement, stale settings, sandbox balance isolation, amount/merchant checks, concurrent callbacks, atomic rollback, disabled-method settlement, payout timeout recovery and exactly-once refunds. It does not contact PayPal/Stripe or send real money. Merchant-specific sandbox acceptance and live approval remain deployment requirements.

## Existing schema and checkout recovery

Startup upgrades early `providerPayments` tables with `flow` (existing records stay on API checkout), `settled`, `settlementRef` and the settlement-reference uniqueness index. Existing terminal payments stay closed. No credentials or balances are reset. A remote checkout created before a local persistence failure can be recovered with **Refresh payment status** or admin **Reconcile**. Stripe recovery reads up to 500 existing sessions, verifies the original reference, user, provider, mode and amount, and restores the checkout link without creating a new payment. An absent session remains uncertain; it is never treated as proof of cancellation.

The payment sidebar shows editable coins/USD conversion, the total including fees, the estimate notice, support and a fixed Buy action. Icon assets come from [Apple Pay’s supplied mark](https://developer.apple.com/apple-pay/marketing/) and [Cash App’s supplied symbol](https://cash.app/press/assets).
